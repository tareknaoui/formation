Rapport d'Audit Architectural BMad

Action Requise (4 Alertes)

Projet: Formation Mandarin | Date: 21 Juillet 2026 | Mode: bmad-architecture validate

Verdict Architectural global

L'architecture de base du projet est saine et bien structurée (Next.js 16 App Router, Prisma 7, NextAuth avec RBAC), mais présente des risques majeurs de performance et de scalabilité en production, notamment autour de la gestion des requêtes SQL dans NextAuth, la connexion PostgreSQL en Serverless et la gestion du modèle d'abonnement.

Pile Technologique

  • Framework: Next.js 16.2 (App Router) + React 19
  • Base de données: PostgreSQL + Prisma 7.8 (Adapter PG)
  • Auth: NextAuth 4.24 (Credentials + JWT)
  • Styles: Tailwind CSS v4

Synthèse des Réseaux / Audit

  • 1 Critique: Requêtes BDD N+1 répétitives dans le JWT NextAuth
  • 2 Élevés: Non-optimisation du Pool `pg` et Modèle Subscription incomplet
  • 1 Moyen: Gestion du streaming vidéo (`videoUrl`)

Détail des Constats Architecturales (Reviewer Gate)

[CRITIQUE] Surcharge BDD dans le callback JWT NextAuth CRITIQUE

Fichier: src/lib/auth.ts (Lignes 67-85)

Description: À chaque vérification du token JWT (ex: à chaque requête interceptée par le middleware), le callback jwt() effectue des requêtes BDD synchrones (db.subscription.findFirst et db.user.findUnique). Cela génère une surcharge massive de la base de données et ralentit les temps de réponse de l'application.

// Problème dans src/lib/auth.ts: const activeSub = await db.subscription.findFirst({ where: { userId: token.id, status: "ACTIVE" } });

Recommandation: Mettre en cache l'état dans le jeton JWT lors du login et rafraîchir l'état uniquement sur appel explicite (via useSession().update() ou webhook de paiement) au lieu d'interroger la BDD à chaque passe du token.

[ÉLEVÉ] Configuration du Pool PostgreSQL (`pg` + Prisma Adapter) ÉLEVÉ

Fichier: src/lib/db.ts (Lignes 12-20)

Description: Le client Prisma utilise new Pool({ connectionString }) sans spécifier de limite maximale de connexions (max). En environnement serverless (Next.js / Vercel), chaque instance va créer son propre pool, risquant de dépasser rapidement la limite de connexions de la base PostgreSQL (ex: Supabase, Neon).

Recommandation: Définir les limites de connexions dans new Pool({ connectionString, max: process.env.NODE_ENV === "production" ? 5 : 2 }) ou utiliser un Transaction Pooler (PgBouncer/Supabase Pooler).

[ÉLEVÉ] Modèle `Subscription` incomplet pour la facturation SaaS ÉLEVÉ

Fichier: prisma/schema.prisma (Lignes 85-94)

Description: Le modèle Subscription actuel manque des champs clés nécessaires à l'intégration d'une passerelle de paiement (Stripe, LemonSqueezy) comme stripeCustomerId, stripeSubscriptionId, stripePriceId, currentPeriodEnd.

Recommandation: Enrichir le schéma Prisma avec les identifiants du fournisseur de paiement et créer un webhook pour mettre à jour automatiquement le statut d'abonnement.

[MOYEN] Stratégie de Streaming Vidéo (`videoUrl`) MOYEN

Fichier: prisma/schema.prisma (Ligne 61)

Description: Les leçons utilisent des liens bruts ou des liens Google Drive dans videoUrl. Cela pose des problèmes de sécurité (téléchargement facile), d'expérience utilisateur (pas de qualité adaptative HLS/DASH) et de quotas de lecture.

Recommandation: Utiliser un lecteur dédié avec un hébergeur vidéo professionnel (Mux, Bunny Stream, Cloudflare Stream ou Vimeo Pro) et stocker un `playbackId` / `videoId` plutôt qu'une URL brute.
